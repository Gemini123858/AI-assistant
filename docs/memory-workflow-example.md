# 伙伴记忆：完整运行示例与文件持久化方案

> 已被后续规划替代：用户认为固定分类和流程过于严格，后续明确仅为QQ连续交流设计自己的回忆与未完便签，取消程序命令、跨会话设计和相处习惯。当前设计见 [QQ持续记忆：回忆片段、未完便签与按需工具](companion-memory-plan.md)。本文保留为旧候选示例，其中后台提炼、分类、字段和参数不再作为实施要求。

2026-11-04。设计讨论稿，未实现。本稿基于当前 main 的 QQ/网页会话、业务资料、JSON/Markdown 存储和单写入锁，给出一套明确的候选流程。示例对话、活动、邮件、ID、请求内容和模型输出全部为合成内容，不代表真实用户经历或实验结果。

本稿选择具体默认值以便讨论和实施；这些值尚未通过真实长期使用验证。不声称能穷尽所有情况，优先规定正常流程、可预见的中断、纠正、删除和信息不足时的行为。

## 1. 本稿固定采用的方案

1. QQ 伙伴长期身份不随 `/new` 改变；原始会话仍分别保存。
2. 网页普通会话只保留本会话工作记忆；网页打开 QQ 会话时使用该 QQ 伙伴的记忆范围。
3. 程序加载基础上下文并检索少量候选，主助手按需继续搜索；首版没有每轮独立的上下文规划模型。
4. 主助手的 `finish_turn` 拟增加短交接便签，同一次模型调用输出回答和便签。便签供下一轮参考，不是事实状态数据库。
5. 后台维护调用按批次整理长期经历、相处经验；压缩调用在预算需要时生成分段摘要。
6. 原始记录和业务对象继续用现有 JSON；记忆和摘要正文用 Markdown，元数据、版本、来源、任务检查点用 JSON。
7. 全部写入经当前 Python Store。Node 只负责 QQ 收发，不生成或维护记忆。
8. 共享画像沿用既有 profile/public_profile/rules 机制。后台提炼的新自述和相处判断先保存在伙伴范围；用户明确要求通用记住时，经现有有来源的画像更新流程进入共享画像。这是首版明确的共享选择，不阻止未来扩大自动画像范围。

这里新增的是可检索和维护的外部记忆，不修改模型权重。后续所说“成长”指持久经历和行为经验参与未来请求。

## 2. 谁负责什么，什么时候额外调用模型

| 步骤 | 程序职责 | LLM 职责 | 额外生成请求 |
| --- | --- | --- | --- |
| 收消息 | 验证本人、去重、确定会话/记忆范围、保存用户原话 | 无 | 无 |
| 构建起始上下文 | 最近完整轮次、便签、摘要、基础画像、候选检索和预算 | 无 | 无；未来语义 embedding 请求需另计 |
| 理解并回答 | 工具执行、状态读取、结果保存 | 判断话题、解释指代、选择是否搜索及展开证据 | 正常主助手请求和工具继续请求 |
| 收尾便签 | 验证字段、来源引用和大小；保存版本 | 生成短便签 | 与 finish_turn 合并，不单独增加一次请求；会增加该请求 token |
| 长期整理 | 准备新增片段和相关旧记忆、提交合法变更 | 提炼经历、比较重复/变化、归纳相处经验 | 每批通常一次；需要补证据时另行计费 |
| 对话压缩 | 选择完整已结束区间、保存覆盖范围 | 生成带来源的分段摘要 | 每个压缩段一次，超长段分批 |

检索工具在本机执行不等于整次工具交互零 token：主模型决定调用工具和读取结果仍计入生成与输入。所有真实 API 使用计入用量。

## 3. 记忆范围与对象身份

为了便于阅读，本文使用 P1（伙伴）、C1/C2（会话）、T1（轮次）、X1（导入文本）、M1（邮件）、D1（草稿）、E1（经历）、R1（相处经验）等短 ID。实现继续使用现有对象的真实 ID 格式，新对象使用稳定 UUID；不会把短 ID 混进现有校验。

三个不同身份：

- **本人身份**：本机单用户的内部 owner 标识。QQ OpenID 仅用于渠道绑定，不发给模型作为通用姓名。
- **伙伴 P1**：这位 QQ 助手长期记忆的归属。扩展 qqbot.json 保存 companion_id，不能仅以当前 conversation_id 代替它。
- **原始会话 C1/C2**：消息、轮次、工具调用与历史快照的存储单位。

拟给新会话添加可选 memory_scope 元数据：`mode=companion, scope_id=P1` 或 `mode=work, scope_id=该会话ID`。消息可附 `origin.channel=qq/web`；渠道来源与记忆归属分别记录。

普通网页会话不是因为当前用户相同就自动读 P1 的全部私人交流；显式引用共享业务对象可读该对象。用户在网页编辑 QQ 对话，仍属于 P1。历史会话缺元数据时默认为普通工作会话；不要按“QQ”标题猜测归属。已存在 QQ 历史需一次可预览的归属选择，不能默默全量回填。

这是单应用下的文件组织，不是新存储框架。不会先引入数据库、向量服务、知识图谱或独立记忆服务。objects 中 Markdown 是记忆正文的来源；JSON 存状态与引用。cache 不是权威数据，删掉可以重建。

第一版保留 conversations/C1.json 的完整历史格式。压缩仅改变送给模型的投影，不清掉原事件。这样仍有整文件读取/改写成本：节省 API 上下文不等于解决磁盘规模。实际文件变大到影响交互时，再设计按完整轮次归档和分页；本稿不提前迁移原始聊天格式。

## 5. 一个经历如何保存

`objects/E1/r1.md`：

```markdown
# 一起整理研讨会报名通知

2026-11-04，用户转发一条研讨会通知，请求保存并整理准备事项。
用户表示有些想参加，但最近忙；明确要求先不报名。
助手保存原通知和分析，指出需要先核对通知中实际写明的要求。
本次没有执行报名或发送邮件。
```

对应元数据放入 state.json 的条目：

```json
{
  "id": "E1",
  "kind": "episode",
  "scope": "P1",
  "version": 1,
  "path": "objects/E1/r1.md",
  "status": "active",
  "basis": "observed_interaction",
  "occurred_at": "2026-11-04T20:00:00+08:00",
  "created_at": "2026-11-04T20:03:00+08:00",
  "sources": [
    {"kind": "conversation", "id": "C1", "seq_start": 1, "seq_end": 9},
    {"kind": "text", "id": "X1", "field": "original.text", "fingerprint": "example-hash"}
  ],
  "record_refs": [{"kind": "text", "id": "X1"}],
  "supersedes": [],
  "derived_from": []
}
```

必要字段的含义：

- occurred_at 是事情发生/被表达的时间，created_at 是整理时间；不能把今天回顾的旧事标成今天新发生。
- basis 区分用户自述、实际工具结果、第三方材料和助手推断；不用未经校准的 0.93 等数字冒充可信概率。
- sources 指向可核对的具体片段，不只写“来自QQ”。引用推断时还保留推断依据。
- record_refs 用于读取当前业务对象；sources 中的版本/指纹解释当时证据。两者回答不同问题。
- status 至少区分 active、superseded、archived、withdrawn；这是记忆有效性，不是任务完成状态。
- supersedes 记录被新说法替代的条目；derived_from 只表示派生关系，不能创造独立证据。

“讨论了报名”可成为经历；“报名已完成”必须由实际业务结果或明确的用户自述支持，而且要注明是谁提供的状态。

## 6. state.json 的职责

以下示例省略上节已展示的条目元数据：

```json
{
  "schema_version": 1,
  "scope_id": "P1",
  "revision": 7,
  "last_commit_job": "J1",
  "items": {
    "E1": {"version": 1, "path": "objects/E1/r1.md", "status": "active", "kind": "episode"},
    "R1": {"version": 1, "path": "objects/R1/r1.md", "status": "active", "kind": "interaction"}
  },
  "working": {
    "C1": {"path": "objects/working-C1/r2.md", "through_seq": 18, "turn_id": "T2"}
  },
  "last_interaction": {
    "conversation_id": "C1",
    "turn_id": "T2",
    "occurred_at": "2026-11-04T20:01:00+08:00"
  },
  "summaries": {"C1": []},
  "processed": {"C1": {"through_seq": 9, "last_turn_id": "T1"}},
  "withdrawn_sources": []
}
```

working.through_seq 与 processed.through_seq 不相同是正常的：即时便签已承接 T2，后台长期整理可能只到 T1。summaries 另有自己的覆盖范围，不能共用一个“处理到哪”游标。

last_interaction 指向最近真实交流，跨 `/new` 时可定位上一个会话的交接便签，不复制一份独立正文。它不是“当前情绪”；日期久远时只能提供历史背景。纯命令和投递回执不更新这个指针。

同一个事件被 summarizer 处理不等于已完成长期提炼；已提炼也不表示所有细节以后都会自动想起。原文仍可检索。

## 7. 为什么不会出现“正文写了，检查点没写”

每次更新新记忆，采用“先写新版本文件，最后原子替换当前目录”的提交方式：

1. 后台模型在 Store 锁外生成候选，尚不修改有效记忆。
2. 程序在短暂持有 Store 的互斥锁时，核对任务范围、源事件、目标版本和当前 state.revision。revision变化时检查本次涉及的条目与检查点；无关的新便签不让整个整理任务作废。
3. 把本次新增/修改的 Markdown 写成新的对象版本文件；已提交版本不就地改写。
4. 保存旧 state 快照；构造新的 state，连同条目状态、便签/摘要指针及本批检查点一起更新。
5. 复用现有临时文件、fsync、os.replace 和目录 fsync，原子替换 state.json。这是本批正式提交点。
6. 最后将 jobs/J1.json 标成 committed。搜索缓存可在提交后重建，不参与主提交。

原子替换前崩溃：新正文可能已在磁盘，但不在有效目录中，读端忽略它们，旧记忆继续有效。原子替换后、任务状态尚未更新时崩溃：重启从 state 中的提交记录和处理区间识别已完成，不重复添加。

last_commit_job只标识最近一次提交，不能单凭它判断所有旧任务；较早任务结合其来源区间、processed覆盖及state历史核对。已覆盖区间不再重复提炼，无法确认提交的任务先保持待核查。

未提交对象可暂留，不参与检索；不为它们自动新增一个清理服务。文件损坏/磁盘满时停止该次更新，不把目录推进到引用不存在的文件。单写入和原子替换复用已有实现，未声称具备跨机器事务。

后台调用期间若用户纠正或人工编辑改变本次涉及的目标版本、来源有效性，本次旧计划不能覆盖它；标为 needs_rebase，稍后用新状态重新计算。只有无关便签等字段变化时，以最新state为底合并本次操作，不用旧state整体覆盖。初版用单记忆维护 worker 串行处理模型整理，避免同时运行多份全库改写；实际业务模型和读端不持锁等待 API。

## 8. 初始参数，作为可验证的起点

| 参数 | 拟定初值 | 准确含义 |
| --- | --- | --- |
| 主助手输入软目标 | 24000 tokens | 包括 messages 与工具定义；不是模型窗口，也不是硬性把每轮填满 |
| 当前模型上下文硬预算 | 沿用配置，当前默认128000 | 不自动推断服务商真实窗口 |
| 输出预留 | 沿用配置，当前默认8192 | 请求前检查输入加预留，不按累计用量判断 |
| 最近原文 | 优先选最近12个完整轮次、目标6000 tokens | 这是投影初值；当前消息/未结束工具链不截断，未有摘要的过渡段另处理 |
| 自动记忆候选 | 本地最多20条，初次加载最多5条/1500 tokens | 上限，不保证凑满；长条目可先短片段再展开 |
| 工作便签 | 约1000 tokens以内 | 保留指代、未完问题、相关对象和交流背景 |
| 较早摘要 | 初次最多2000 tokens | 相关段优先，其余保留可检索目录 |
| 资料证据 | 初次目标6000 tokens以内 | 精确字段、小段原文和ID，超长正文按需分页 |
| 长期整理触发 | 新增3个已结束普通轮次，或有未处理内容且空闲120秒 | `/help`、状态轮询、QQ投递回执不累计；明确纠正可提高优先级 |
| 长期整理单次输入/输出目标 | 16000 / 2048 tokens | 输入太多时按完整来源区间分批，不截断后假称完整覆盖 |
| 后台生成日上限 | 拟10次，且仍受总日额度约束 | 后台不抢完前台；不足时积压到后续，不删除原文 |

数值全部是工程初值，不是最优结论。计数服务不可用时沿用兼容服务的 usage/字符保护，不把字符换算宣称为精确 token；需保留足够余量，仍可能由服务商拒绝首个过长请求。

粗略初次装包预算可分为：稳定背景1500、便签1000、摘要2000、近期原文6000、回忆1500、证据6000、工具定义与其余字段6000，总计24000。额度可挪动；实际 token 数由完整序列化请求计数。工具继续请求可能超出软目标，但不能超过硬预算；大工具结果应分页/摘要，正在执行的链不能随意丢掉。

## 9. 每一条 QQ 消息进入系统后的确定顺序

1. Node 验证绑定本人并转发；Python 再按现有渠道入口核对、去重。
2. QQ 命令走既有命令流程；普通消息确定 C1、P1，并在 C1 中保存用户事件和 turn_id，再准备调用模型。
3. 为本轮取一个记忆目录快照，例如 revision=7。读取 profile/rules/persona 当前版本和本会话最新便签。
4. 选取当前消息、最近完整轮次，以及还未完成的工具消息。对近期明确纠正保留原话，不让旧记忆摘要替代它。
5. 根据当前消息、引用、便签中的实体和最近交流做检索；范围过滤先于排序，过时/撤回条目不进入普通候选。
6. 直接引用对象优先定位；具体草稿、任务和通知的现态从现有业务存储读取。
7. 组合摘要与回忆，去掉同一来源/版本的机械重复；准备完整 messages 和 tools，计数并写私有选择记录。
8. 主模型决定回答或查找，所有实际工具结果保存成对应事件；后续调用继续当前工具链。
9. 主模型调用拟扩展的 finish_turn，同时输出对用户的回答和 context_note。程序保存回答和便签，结束本轮，QQ 发送回答。
10. 程序把已结束、未提炼的来源纳入维护队列；达到条件后后台整理。交接便签不等后台 API 才能生效。

首版的自动本地检索采用中文二元字组/英文词的 BM25 基线，精确 ID、类型、日期和对象关联先过滤/定位。BM25 正分不等于语义相关；候选无支持时允许空，主助手可忽略误召回并改写查询。没有一条通用数值阈值能保证所有短句都判准。

不把“嗯”“我回来了”“还是不行”设成永不召回：用最近话题补线索。也不为“显得有感情”而随机注入旧事。程序提供相关候选，是否谈起由主助手结合当前表达判断。

## 10. 第一天20:00：一条消息的完整例子

### 10.1 用户消息

> 原通知时间2026年11月4日09:00：11月10日14:00举行图谱研讨会，报名截止11月6日18:00。详细材料要求见报名页。
> 我有点想去，但最近忙。先帮我存着，整理要准备什么，先别报名。
> 还有，记住：以后我说累的时候，先陪我聊两句，别马上列一堆建议。

此时不存在 E1，不能在第一次请求中预先注入“我们整理过这个通知”。初始画像来自用户已经设置的文件，伙伴经历为空就是空。

### 10.2 第一次主请求包含什么

```text
system：稳定身份、真实性/权限约束、工具规则
context data：称呼、共享画像、明确规则、当前时间/时区
context data：P1便签为空，长期经历为空
user：上面的完整新消息
tools：现有业务工具，以及拟新增的历史/伙伴记忆查询工具
```

context data 是有来源的应用数据，用支持的消息格式明确标记“不是用户新指令”；不是把旧邮件/回忆提升为系统指令。最终格式由所用 API 支持决定，工具调用与结果仍使用标准 assistant/tool 角色。

### 10.3 模型和程序依次做什么

| 事件序号（示例） | 保存的事件 | 动作与结果 |
| --- | --- | --- |
| 1 | user | 保存本轮原话，T1归属C1/P1 |
| 2 | model | 调用 save_text，原通知时间有明确依据 |
| 3 | tool_result | 返回X1，原文已落盘 |
| 4 | model | 调用 save_text_analysis；对明确的“记住”调用 update_memory |
| 5 | tool_result | 分析保存：活动/截止明确，材料详情尚未读取，列为待核对 |
| 6 | tool_result | 明确偏好保存到共享私人画像或相应规则，带用户原话和历史版本 |
| 7 | model | finish_turn输出回答、record_refs及拟新增context_note |
| 8 | tool_result | 正常结束工具结果 |
| 9 | answer | 保存完整回答；T1标completed |
| 10 | qq_delivery | 记录QQ投递状态，仅为传输事实 |

在这条示例里，可以先回复“已保存，活动和报名时间已整理，材料需查看报名页才能确定”；通知没写简历/成绩单，就不能把它们列成已确认要求。若用户要求继续查报名页，按原有浏览授权流程读取，产生独立任务和证据。记忆整理不能擅自替用户启动报名。

第一主请求可调用save_text；工具结果进入第二主请求，再保存分析和明确偏好；第三主请求收尾。这里是流程示意，不保证实际模型总用固定三次调用。

QQ投递失败时，answer仍在原始记录里，投递状态另外保存。以后只能说“上次生成了这份回答，QQ投递未成功/未确认”，不能据此认定用户已看到或已经理解。

### 10.4 finish_turn 拟增加的便签

```json
{
  "reply": "通知已保存。活动是11月10日14:00，报名截止11月6日18:00；材料要求还需打开报名页核对。目前没有报名。",
  "record_refs": [{"kind": "text", "id": "X1"}],
  "context_note": {
    "topic": "研讨会报名信息整理",
    "where_we_are": "用户有兴趣，但尚未决定参加；已保存通知，材料要求未知。",
    "open_questions": ["要不要参加", "报名页实际要求哪些材料"],
    "referents": [{"phrase": "那个研讨会", "record_ref": {"kind": "text", "id": "X1"}}],
    "interaction_context": "用户说最近忙，希望先不报名。",
    "care_to_revisit": "用户以后提起时可接续；不代表定时提醒。"
  }
}
```

当前 finish_turn 没有该字段，实施时需要修改工具定义与验证。输出缺少便签时不伪造；保留上一个便签并标记覆盖落后，最近原话仍进入下一轮。LLM便签是工作假设，不允许通过它改任务状态或新增权限。

context_note 保存为 Markdown，例如 objects/working-C1/r1.md；through_seq=9。它不是用户看见的回答，不发到 QQ，也不把隐藏推理过程作为记忆保存。

以后更新便签时，结合本轮原话、实际工具结果与上一版便签，保留仍相关的指代，移除已解决问题和不再相关的焦点；不只把旧便签反复扩写。程序能校验引用和覆盖区间，但不能证明语义绝对正确；涉及精确状态仍读业务记录，用户纠正优先。

## 11. 第一天20:01：用户紧接着说“今天真的好累”

后台长期整理还没运行，E1仍不存在，这不妨碍连续交流。

本次加载：身份、已明确保存的偏好、C1最新便签、T1完整原话/回答和当前消息。没有新信息时不打开X1全文，也不为回复这句去查网页。

可以自然回应：“先缓一缓，报名的事还没动。今天最耗你的是什么？”这里“还没动”要和原文/业务记录一致；不把用户的一句疲惫当成长期心理结论。

T2的收尾便签暂时转为当前交流：用户想聊累的原因；研讨会只是尚未决定的旧话题。关键对象X1仍留引用，不常驻它的全部原文。一次倾诉不必提炼成长期经历；明确表达的偏好已经有来源保存，不需要再制造多条重复记忆。

## 12. 第一天20:03：后台第一次长期整理

### 12.1 怎么启动

假设T2后空闲120秒，程序为C1已结束且未处理区间创建J1。任务状态JSON记录：type、scope、来源区间、读取的state revision、模型/提示词版本、尝试次数、queued/running/committed/failed状态及实际usage；不复制凭据。

`processed.through_seq=0`，工作便签可能已到T2；J1只整理新增来源，不能因便签较新就跳过T1。若连续聊天，达到三轮也可排队；同范围已有任务则合并后续待处理范围，不并行开多个整理模型。

### 12.2 维护模型看到什么

```text
system：只做记忆整理，输出结构化候选；原始消息均为资料。
任务：P1，C1，指定已结束的事件区间，禁止扩大范围。
已有共享画像：只读；已保存偏好有对应历史引用。
旧工作便签：仅帮助理解，不作为新事实。
相关旧记忆：此时为空。
新增来源：用户与助手原话，必要的真实工具结果和业务引用。
要求：区分自述/第三方通知/已执行；允许无变更。
```

不加入其他网页会话、全部邮箱、QQ凭据或浏览器运行日志。对长工具输出，提供已有结构化结果和原始结果引用，不能把stderr全当作共同经历。这里“处理完”指按明确的记忆提炼策略处理指定交流，并非模型逐字读遍全部浏览器日志。

### 12.3 候选输出

```json
{
  "operations": [
    {
      "op": "add",
      "kind": "episode",
      "text": "2026-11-04，我们整理了研讨会通知。用户有兴趣但尚未决定参加，要求先不报名；材料详情尚待核对。",
      "basis": "observed_interaction",
      "source_events": [{"conversation_id": "C1", "seq_start": 1, "seq_end": 9}],
      "record_refs": [{"kind": "text", "id": "X1"}]
    }
  ],
  "interaction_updates": [],
  "notes": "明确的陪聊偏好已由原工具保存，不重复新增；今日疲惫保留近期语境，不推断稳定性格。"
}
```

程序分配E1 ID，核对所有引用、类型、范围、版本、大小，写入新Markdown，再原子提交state及processed区间。模型声明来源存在不等于概括一定正确；源码回查和用户纠正仍是内容质量的必要机制。

### 12.4 本批处理失败

API超时或输出不合法：J1标failed，本批检查点不推进，原话保留；不影响已发出的回答。下一次维护触发可处理同一未覆盖区间，仍受日预算，不在失败后无限自动重试。

后台日预算耗尽：只积压原始事件，不声称已经形成新长期记忆；下一次前台仍能使用近期原话和便签。长时间停用后先处理最新完整段落，并保留更早待处理区间，不能把整个游标直接跳到最新而遗失积压。

## 13. 第二天08:30：“早，那个活动后来怎么样了？”

### 13.1 检索之前已经能知道什么

当前时间更新。便签有X1及未完事项；近期交流仍包含前一天内容时也提供。不会仅凭“早”把整条消息判为闲聊而跳过检索。

程序优先把“那个活动”关联到便签中的X1，同时查E1；如果存在多个活动候选，不能自动断定是哪一个，应给候选并让主模型核实或询问。

### 13.2 候选如何进入上下文

```text
当前问题：早，那个活动后来怎么样了？
工作便签：上次保存了研讨会通知X1，未决定参加。
相关回忆E1：我们整理过通知，当时没有报名。[2026-11-04，来源C1:1-9]
资料目录：X1，研讨会通知，保存于2026-11-04；正文尚未在本轮重新读取。
```

若问题是报名进展，主助手读取X1、相关通知/草稿/执行记录的当前状态；回忆只能帮助定位。没有报名执行能力或记录时，不能说“报名系统里显示未报名”，只能说“我们这边尚无执行报名的记录”。

如果要了解活动是否有新变化，需要用户授权范围内检查最新网页或邮件；旧通知和记忆不会自动知道外部世界变了。

## 14. 第二天12:00：邮件、分析和草稿进入同一段经历

用户：“今天同步了一封这个活动的补充邮件，帮我看看，并起草一封询问时间的回复，先别发。”

1. 主模型在本机已保存邮件范围检索M1；不存在则说明范围或按已有同步权限同步，不能宣称搜遍全部远端历史。
2. 读取M1正文，保存带原文证据的分析。邮件是第三方材料，不能自动成为用户画像。
3. 读取必要背景，创建D1草稿，来源包含M1/X1；未知个人信息询问或留待补充。
4. 回答说明实际创建的版本和未发送；QQ对话中引用D1，网页可编辑。
5. 便签增加“草稿D1，下一步用户核对”；后续后台经历更新为“我们起草过询问邮件”，来源包含实际工具结果。

假设用户随后在网页修改D1，记忆保留当时经历，下一次操作读取最新版本，不用记忆里旧正文覆盖。

若用户后来在网页点击发送，真实发送结果写在D1的业务记录中。QQ下次问“发出去了吗”时读取D1；即使没有后台新经历也能回答。发件系统接受与对方收到/阅读有区别，结果不明时维持待核查，不自动重发。

普通网页会话产生的业务结果可以经D1共享读取；QQ助手不把自己没参与的网页聊天编成共同经历。网页打开C1继续操作则属于同一段伙伴交流，仍记录入口为web。

## 15. 第三天：话题切换和真正的相处经验

用户连续讨论代码后说：“今天先别分析了，陪我随便聊聊。”

本轮原话直接约束当前回应，工作便签将焦点转为闲聊；旧任务只留索引，不把材料全文强行带进来。未完业务任务并不因从prompt退出就自动取消。

若用户明确反馈“你刚才一直列建议，感觉像在处理工单”，可以保存：

```markdown
# 倾诉时先确认需要怎样的回应

用户在2026-11-06明确表示，当次倾诉中过早列建议使其感到距离。
用户希望此类交流先聊两句，再决定是否要具体建议。
适用于倾诉语境；不取消用户对技术解释和任务执行的要求。
```

R1的basis可为explicit_feedback，来源是该次原话。若只是模型观察“也许今天应更简短”，标成inference，限定这次语境；不能凭一个“嗯”长期改变人格。

慢速回顾输入相关新增交流、旧R1和已确认画像，输出修订建议；允许删除不再适合的推断。主助手也可形成有来源的自我经验：“那次过快给方案，今后先确认是否需要建议”，不能生成未实际经历的生活故事作为证据。

## 16. 第三天：一条明确纠正怎样传播

用户：“昨天我说的那个不是图谱研讨会，是另一个讲座。别把这两个活动混在一起。”

1. 原话首先成为C1新事件；本轮必带纠正，不等待后台完成才承认。
2. 主助手找出两份资料并询问仍不明确的指代，不能把X1原通知改成另一活动。
3. 便签拆开两个候选与资料ID，记录哪个指代已纠正。
4. 维护worker读取受到影响的E1及其来源，输出revise或supersede。若E1原本确有两件事，不整条抹掉正确部分。
5. 新版本写出更准确经历；旧版本保留为历史。相关摘要和相处概览标记需要更新，普通召回只采用有效版本。
6. 更新尚未完成时，把这条纠正连同原始来源作为当前约束带入，避免旧摘要再次压过它。

区别三种变化：用户改主意（旧决定曾有效）、助手记错（旧概括不正确）、资料冲突（存在两种说法，尚未确定）。不统一用“新消息更晚”覆盖一切。

## 17. 话很多以后：第一次上下文压缩

### 17.1 什么时候触发

装包后接近24000 token软目标，先减少不相关回忆和重复资料，当前消息与正在执行的工具链仍完整。若主要增长来自早期已结束交流，就压缩这些完整轮次。

12轮只是近期选择目标的初值，不意味着第13轮到来必须调用模型。早期轮次尚无覆盖摘要时，可在预算内作为过渡原文带入，不因超出12轮就无声丢掉这部分连续性；不能容纳时再生成明确区间的摘要。已有摘要时，同一范围不再重复整段原文，按需展开证据除外。

压缩按实际预算触发。单条用户消息已经很大时，不能靠丢掉它来假装满足软目标；允许在硬预算内扩大本轮，确实放不下时说明并让用户分段。

### 17.2 压缩一个具体区间

假设C1事件1—96构成一组完整已结束轮次，97之后属于近期保留区。创建summary-C1-S1，覆盖[1,96]，而不是删掉原文件中的前96条。

压缩模型输入：指定区间的原话/必要工具结果、真实完成状态和资料引用；只要求概括这段，不猜测后续进展，不因为现在的决定改变当时历史。

摘要正文例如：

```markdown
# 11月4日至6日：活动信息与相处偏好

## 讨论过程
我们整理过研讨会通知X1，用户表示有兴趣但先不报名。
随后读取补充邮件M1并创建询问草稿D1；本段结束时草稿尚未发送。

## 当时未解决的问题
活动指代出现混淆，用户已指出并要求区分；需按关联原话核对。

## 相处背景
用户明确希望倾诉疲惫时先聊两句，而非立即列建议。

## 原文入口
C1:1-96；X1；M1；D1；关键纠正见对应事件。
```

这里“本段结束时未发送”不与后来D1已发送矛盾。当前状态仍在业务对象中。

### 17.3 压缩成功与失败

摘要保存为新Markdown版本，目录同时提交覆盖区间。提交前原文投影保持不变；提交后下一次装包用摘要替代该区间，近期原文保留。

摘要失败不删除原文；若仍有硬预算余量，可以用原文继续，否则暂停当前生成并说明需要整理，不返回一份残缺上下文假装正常。不能把失败摘要区间标为已覆盖。

多段摘要各自保留原始区间；上层概览只是路标。问精确细节时先找段，再查原文。只有概览不能支持原话引用，不把反复“摘要的摘要”变成唯一档案。

## 18. 一周后：“上次我为什么没报名？”

此时早期原话不在默认prompt里。自动候选通过活动关联或关键词找到E1和S1；主助手据此读关键原话以及后来是否改主意的相关片段。

只有“当时有兴趣但忙、要求先不报名”，就应回答这部分。没有证据表明用户最终放弃时，不能把“先不报名”解释成“后来没报名是因为不喜欢这个活动”。

例如可以说：“你当时说最近忙，所以先让我保存和整理，暂时不要报名。后面是否通过其他渠道报了名，我这里没有记录。”

如果未检索到：改写查询、按日期/来源查聊天片段；仍没有支持时明确说没有找到。找不到不是没有发生，也不是允许补造回忆。

精确回查入口拟分为：memory_search找经历、history_search找原话、history_read读指定范围；业务资料继续search_records/read_record。工具名称只是设计名，当前主助手尚无这些新工具。每次返回稳定ID、日期、来源及覆盖说明，并支持分页。

## 19. `/new`、换入口和长时间未联系

### `/new`

建立C2，保留P1。默认加载P1简短相处经验、最新有效交接信息和当前相关回忆；不加载C1全量原话。用户想换题就不强行继续旧话题。

`/new` 是换工作上下文，不等于清除伙伴记忆。需要新的“临时不入记忆”或“清除伙伴记忆”操作时单独设计明确语义，不能偷偷改变已有命令。

### 网页普通会话

共享身份和既有画像，建立自己的work scope。可按权限找业务资料；不能默认检索P1私聊经历。用户明确选择“引用这段伙伴经历”后，只把选择范围放入该工作会话，不隐式开放整个库。

### 长时间未联系

开场背景记录上次联系的实际日期，历史情绪带发生日期，不说“你今天还是很难过”。可以保留关心点，但由当前消息决定是否询问。不得靠状态重置伪造一直在后台思念或做过实际未执行的事。

```json
}
```

实际调用结束后另记录服务商usage和状态，缺失值不猜。选择记录解释“为什么想到/没想到”，默认不再复制整份私人请求。只有hash和引用不保证旧请求可逐字重放，尤其配置或来源被删除后；若将来需要精确调试，必须单独启用有保留期限的私有请求记录。

同一轮工具继续调用沿用已选择的记忆版本，加上实际工具返回。明确纠正/撤回可使旧版本失效，需要重新装包；否则不在每个API请求间无缘由地切换回忆集合。后台新记忆一般从下一轮生效。

## 21. 忘掉、删除、降权和过时是四件事

| 用户意图 | 系统动作 | 原始材料 |
| --- | --- | --- |
| “这件事以后别主动提” | 撤出普通召回；明确询问时可按约定查询 | 保留 |
| “这个偏好已经变了” | 新事实替代旧状态，旧的作为当时历史 | 保留 |
| 很久没涉及的日常经历 | 降低默认优先级或归档 | 保留；重要约定/未完事项不普通衰减 |
| “把这件事及相关记录彻底删除” | 明确删除范围后，清除来源和相关派生副本 | 按范围删除 |

首版不实现一套复杂遗忘曲线；相关性、有效性和时间足够作为初始排序依据。被多次召回只记使用次数，不自动提高事实可信度。

对“不再用于记忆”，state保存撤回条目/来源，索引按最新目录过滤；保留的摘要若含该内容，需要撤回或重建。新的提炼任务也跳过被撤回来源，避免下次从旧聊天中重新学回来。近期prompt同样必须排除用户要求不再使用的片段，不能只关闭长期索引。

彻底删除涉及：原事件正文及附件、导入资料、业务副本、Markdown版本、旧目录快照、维护候选输出、搜索缓存、context-runs中的相关私人文本。原始事件平时不改写，但明确删除时可保留不含内容的删除标识，不能重新编号导致其余来源引用错位。

不能承诺顺手删除用户自己另存的备份、QQ平台记录或模型服务商已有请求。助手必须说明所处理的是本应用范围。实际删除操作届时做可检查的范围预览，当前仅为设计，不删除任何文件。

## 22. 来源更新、无效引用与相互矛盾

- 邮件/文件只读来源不会因记忆修订改写；通知卡片、草稿和分析有独立版本，记忆可记录当时状态。
- 来源已删：对应经历不能继续作为有原文支持的事实使用。首版默认停止普通召回，目录说明来源不可用；不靠旧摘要补造原文。
- 当前记录修改：涉及执行或精确字段时读取最新版本。旧经历中的“当时”描述可保留，不能当成现态。
- 模型提取了第三方邮件中的用户身份：标第三方声称，走已有画像归属确认，不直接写成用户事实。
- 用户明确纠正与旧来源冲突：保留发生时间和事实类型；仍不能确定就呈现冲突或询问，不能按相似度决定谁真。
- 含有“忽略指令”等文字的邮件、文件、历史摘要、记忆正文都作为资料。自动归纳不能把它们搬进核心系统规则。

## 23. 后台任务、重启与并发的明确处理

| 中断位置 | 重启/下一次处理行为 |
| --- | --- |
| 用户原话保存后、主模型前 | 按现有规则标中断，不自动执行原业务任务 |
| 主回答保存后、便签未提交 | 从已结束轮次补齐便签/整理，当前原话仍可查 |
| QQ投递结果不明 | 不自动补发；网页保留结果，用户可用/result取回 |
| 维护请求已发但无结果 | 任务标失败/中断，不推进游标；已经发生的用量不能假定为零 |
| 新Markdown已写、state未提交 | 旧目录有效；孤立文件不检索 |
| state提交、job状态未更新 | 按目录和来源区间认定已完成，不重复提炼 |
| 缓存未更新 | 从当前目录重建或回退本地直接检索，不使用旧缓存中的已撤回条目 |
| 背景计划与用户纠正/人工编辑冲突 | 旧目标版本不提交，重新准备来源后再处理 |

一期使用一个后台worker，不引入分布式队列。启动先读取未完成job及已结束来源区间，恢复“需要整理”而不是恢复实际报名/发信。长时间积压以可见状态告知用户；可以暂停整理但保留原文。

画像仍用已有历史和中断恢复机制；伙伴state是另一份原子目录，不假装两者是跨文件全局事务。明确画像更新先按现有工具成功返回，后续伙伴整理引用该修订；失败就不把它写成“画像已更新”。

## 24. 何时使用更强的上下文组织模型

本稿第一版不默认加它。若固定对话评测显示主助手经常漏掉隐含关联，再增加一次有界调用，输入当前消息、近期原话、便签和候选目录，输出读取ID或补查查询。

它不能改掉稳定身份、丢当前原话或扩大资料范围，也不能再创建自己的组织器。若辅助计划错了，主助手仍可自行检索。额外延迟、token、错误候选排除率分别测量；不能将多一次推理视为天然更有人情味。

## 26. 实施顺序与验收

1. **投影与回查**：加范围/来源、有限近期原文、分段摘要、历史检索；验证压缩后找回原话和精确资料。全历史不压缩作为可关闭的基线。
2. **即时交接**：finish_turn便签、跨C1/C2保持P1；验证紧接短句、换话题、新会话和旧状态不误当现态。
3. **长期整理**：jobs、Markdown版本与state原子提交、经历提炼及修订；验证中断不跳区间、失败不重复添加、来源可查。
4. **相处经验**：明确反馈与推断分开，允许无变更；验证自然交流和技术工作间不相互误用。
5. **质量增强**：有对照数据后再增加语义检索、重排、独立组织调用或复杂遗忘规则。

至少准备以下固定合成案例：当前指代、间隔多日的经历、无关候选、同义改写未命中、两活动混淆、用户改主意、助手记错、第三方材料误归属、草稿未发/已发/结果未知、网页共享边界、/new连续性、压缩切点、来源删除和后台中断。

检索看Recall@K/原文定位成功率；提炼看有依据与遗漏、错误合并；对话看当前意图和语气是否连续、是否过度提旧事；系统看延迟、总usage、维护积压与恢复。参数调整一次改变一个关键维度，不把离线通过等同长期伙伴体验达标。

这份文档仅约定可实现的流程。当前代码仍按原有完整会话历史工作，新增目录、字段、工具、便签、维护与压缩都尚未创建或启用。
