# 统一助手入口：产品方案与实现计划

日期：2026-10-29。

状态：统一方向、独立业务记录与跨会话引用关系已由用户确认。U1～U4 的首版代码已在 `feat/unified-assistant` 实现，合成流程验证通过，待用户接入真实 API 验收，尚未合并到 `main`。本文保留产品设计基线；具体落地与首版限制见第 9 节。

## 1. 要解决的问题与交付目标

当前通知问答、网页任务追问、邮件追问、草稿编写分别维护入口和上下文，用户需要自己选择功能、搬运资料和衔接任务。单纯将聊天框摆到同一页，不能解决底层会话和能力割裂。

交付目标是：用户在一个聊天入口提出目标，可以添加已有资料，助手在同一会话中调用所需能力，完成跨类型任务；结果可以追溯、继续修改和跨会话复用。需要编辑或发送邮件时，在当前会话的详情面板完成，不要求跳转到邮箱工作台。

已确认的要求：

- 聊天成为主要操作入口，提供持久化的多会话历史，每个会话有自己的上下文。
- 主助手可以使用整套业务能力，不根据“邮件会话／网页会话”等类别划分功能权限。
- 一轮用户交互可以调用多次模型、执行多个不同类型操作，并产生多份业务记录。
- 会话与业务资料独立；不同会话可以引用同一份草稿、通知或网页查询结果。
- 同一份草稿可以持续修改并保留版本；修改当前产物不改写历史交互内容。
- 第一版完整拼接本会话的上下文，不先做历史摘要、自动裁剪或向量检索。
- 保留现有读取范围、公开浏览与私人分析的边界；邮件发送继续由用户检查当前版本后点击触发。

本次不同时扩展网页表单提交、新邮箱、新接入、附件解析、主动推送或统一事项系统。视觉样式可以逐步完善，但资料选择、结果打开、编辑和发送的位置必须在统一入口中形成闭环。

## 2. 用户界面与逐步操作

### 2.1 主界面

```text
┌──────────────┬──────────────────────────────────┐
│ ＋ 新对话     │ 暑期项目申请                      │
│              │                                  │
│ 历史会话     │ 用户消息、执行进度、助手回答        │
│ 暑期项目申请 │ 以及关联的业务记录                 │
│ 查找实习     │                                  │
│ 课程通知整理 │                                  │
│              │ 已添加：[项目邮件 ×]              │
│              │ ┌──────────────────────────────┐ │
│ 资料管理     │ │ 输入要求……                   │ │
│ 设置         │ └──────────────────────────────┘ │
│              │ [＋ 添加资料]           [发送]   │
└──────────────┴──────────────────────────────────┘
```

- 左侧提供新建、切换、重命名和删除会话；标题初期取首条用户消息，不额外调用模型命名。
- 中间是当前会话，输入区保留在易于访问的位置。普通聊天不需要先选功能或资料。
- 刷新后恢复当前会话；退出登录不删除会话。重新登录后可继续查看。
- 资料管理负责集中浏览与维护通知、邮件、网页记录、草稿；设置负责配置状态、画像与规则。它们不再各自维护聊天框。
- 桌面点击业务记录后在右侧打开详情面板；手机采用覆盖式面板，关闭后回到原会话位置。

### 2.2 添加已有资料

默认操作路径：输入框旁“添加资料” → 弹出选择器 → 选择类别／搜索 → 预览、勾选 → “添加到消息”。不要求切到其他页面逐一选择。

选择器包含邮件、通知、网页任务结果和草稿，默认列出最近记录，支持按类型、标题、日期、发件人及正文关键词查找。先使用现有文件扫描和普通匹配，不引入语义检索。搜索结果只展示摘要和元数据，预览时读取正文。

添加后，输入框上方出现可移除的资料标签。发送时由服务端读取实际记录、保存引用和内容快照；不能仅传 ID 却让模型看不到正文。已发送的资料属于该条历史消息，移除下一条消息的待发送标签不会删除过去的资料。

资料管理中的“加入当前会话”是辅助入口，效果同上。粘贴的文字和链接也可直接随消息发送；除非用户要求保存，不自动把每段聊天文本创建成通知。

用户也可以不手动选择，直接说“找一下昨天招生办公室发来的项目邮件”。助手搜索已保存邮件并按需读取。无法明确区分候选时，在聊天中展示候选供选择，不猜测目标。

“搜索邮件”默认搜索本机已保存的范围，不宣称覆盖整个远端邮箱。同步和导入历史邮件继续沿用当前明确的范围，不能借统一入口静默扩大历史读取范围。

### 2.3 一轮跨类型任务

示例要求：

> 看看这个项目是否适合我，查一下官网申请要求，再起草一封邮件询问大三学生能否申请。

操作与反馈：

1. 新建会话，添加项目邮件，输入要求并发送。
2. 用户消息立即保存和显示；输入区显示本轮运行状态及停止入口。
3. 助手读取邮件、调用网页查询、接收网页结果，再创建草稿。进度来自真实执行事件，不提前伪造已完成步骤。
4. 最终回答给出适配判断、证据和未确认项；下面展示网页结果、邮件草稿等关联记录。
5. 点击网页结果“查看详情”，核对结果与出处，关闭面板后仍在本会话。
6. 点击草稿“查看并编辑”，在详情面板修改；也可以继续聊天要求修改同一份草稿。
7. 用户检查当前收件人、主题和正文，点击“发送当前版本”；面板和会话记录实际结果。
8. 隔天重新打开该会话，原资料、查询结果、修改记录和发送状态仍可查看并继续讨论。

网页查询失败不意味着整轮所有操作都失败。助手可以根据已有邮件继续起草，同时明确哪些要求没有核实。执行已产生的记录保留，不因最后回答失败而丢弃。

### 2.4 最小结果展示与后续操作

第一版使用最终回答加关联记录列表：

```text
助手：官网没有明确说明大三学生是否可申请，咨询草稿已准备，尚未发送。

本轮结果
✓ 官网查询：项目申请要求       [查看详情]
✓ 邮件草稿：咨询申请资格       [查看并编辑]
```

| 记录类型 | 展示与操作 |
| --- | --- |
| 邮件 | 主题、发件人、时间；查看原文及已保存分析 |
| 通知 | 标题／来源、时间；查看原文及已保存分析 |
| 网页任务 | 状态、结果、出处；查看执行日志，运行中可取消；重新查询产生新任务 |
| 草稿 | 主题、状态、当前版本；查看并编辑、查看历史、复制为新草稿、发送当前版本 |
| 画像变更 | 保存内容、归属与来源；查看、纠正或撤销 |

“继续查询”“根据这个写邮件”等组合任务优先通过聊天表达，不为每种组合增加按钮。一个会话关联多份草稿时，详情面板明确显示当前打开对象；发送消息可以附带该对象引用。没有明确指代时，助手应请求选择，不能随意修改另一份草稿。

## 3. 会话、执行与业务资料的关系

### 3.1 三种对象

| 对象 | 职责 | 生命周期 |
| --- | --- | --- |
| 会话 Conversation | 保存交互顺序、资料快照、工具调用与返回、最终回答和用户界面操作 | 持续追加；与业务资料分别删除 |
| 执行记录 Run / Operation | 保存一轮工作及其中各次工具执行的输入、状态、结果引用和错误 | 运行时更新状态，终态结果保留；重试是新执行 |
| 业务资料 Record | 保存邮件、通知、网页查询结果、草稿等真实内容 | 独立保存；是否可修改取决于类型 |

Run 表示一次用户请求的整体执行，Operation 表示其中一次工具调用。它们是需要表达的概念，不要求第一版各建一套独立存储框架：轮次状态、操作元数据和结果快照可以直接存进会话文件；浏览器内部动作继续存在网页任务文件里。

一份业务资料可被多个会话引用，一轮会话也可创建、读取或修改多份业务资料。业务记录可以保存创建会话和轮次的出处，但不能把出处当成“只允许这一会话使用”的所有权。

### 3.2 草稿例子与版本规则

```text
会话 A 第 1 轮 → 创建 D1 v1，保存本轮结果快照
会话 A 第 2 轮 → 修改 D1 为 v2，追加修改结果
会话 B 添加 D1 → 取得当前 v2，并保存加入时的快照
会话 B 修改 D1 → 产生 v3
会话 A 打开 D1 → 看到当前 v3，同时可以查看历史 v1 / v2
```

- 引用默认指向同一对象，修改共享；“复制为新草稿”创建新的 ID，之后独立修改。
- 当前编辑器展示最新版本；历史消息保留当时的版本、输入和结果，不动态覆盖历史内容。
- 打开旧会话时可提示“当时 v1，当前 v3”。给模型的旧工具结果也保持原样。
- 修改前必须读取当前草稿，并携带当前版本保存；复用现有版本校验。检测到版本变化时重新读取，不拿旧快照覆盖新内容。
- 手工修改、恢复历史、发送等界面操作也要进入当前操作会话。其他引用该对象的会话在下次调用模型前获知当前版本变化，无需复制另一会话的聊天内容。
- 草稿详情的未保存输入必须保全。建议短延时自动保存并显示保存状态，切换对象或发送前等待保存完成；失败时保留输入并显示可重试状态，不静默覆盖。具体自动保存间隔在界面实现时确定。

### 3.3 不同记录的修改语义

- 邮件、通知的原文作为来源保留；重新分析更新派生分析，操作快照保存当时结果，不篡改原文。
- 网页任务保留本次请求、动作、页面证据和最终结果；补查／重跑生成新的网页任务，并关联原任务，不覆盖旧证据。
- 草稿保留同一 ID 下的版本历史；发送状态与实际发送内容可以追溯。
- 第一版不强制为所有来源引入通用版本系统；没有版本号的内容快照可使用内容摘要和获取时间定位。

删除会话默认只删除会话历史及引用，不删除独立业务记录。删除业务记录是单独操作；其他会话仍保留已形成的历史快照，并显示当前对象已不存在，不能继续编辑。删除会话不是清除所有关联私人数据的入口，界面需明确说明该范围。运行中的会话先停止再删除。

## 4. 统一记录表示与上下文

### 4.1 中间层职责

增加一个小型、确定性的记录转换模块，按记录类型读取和生成统一表示。它同时服务资料选择、工具返回、上下文组织和界面展示，但不要求这些场景使用同一段字符串。

建议表示字段：

```json
{
  "ref": {"kind": "draft", "id": "D1", "version": 2},
  "title": "咨询申请资格",
  "status": "draft",
  "updated_at": "2026-10-29T10:00:00+08:00",
  "data": {"from": "owner@example.com", "to": [], "cc": [], "bcc": [], "subject": "咨询申请资格", "body": "合成示例正文"},
  "source_refs": [{"kind": "mail", "id": "M1"}],
  "coverage": {"complete": true, "notes": []}
}
```

示例 ID 是说明用占位符，实际沿用程序生成的稳定标识。各类型的 `data` 保留自己的字段；不把邮件、网页和草稿硬塞成一套正文格式。工具返回还要标注是否截断、是否只含邮件头、哪些附件未处理等事实。

界面摘要由上述结构生成，编辑按钮由前端按类型和服务端能力状态提供；操作是否允许仍由服务端判断。转换本身不调用 LLM，不把模型生成的短摘要当成唯一权威数据。

### 4.2 会话保存示意

建议 `data/conversations/<id>.json` 保存一份会话的元数据、顺序事件和轮次状态：

```text
schema_version、id、title、created_at、updated_at
turns：轮次 ID、运行状态、时间、取消请求、预算／用量
events（按 seq 排序）：
  用户消息：文本、资料引用和加入时快照
  助手消息／工具调用：对应轮次、调用 ID、参数
  工具结果：对应调用 ID、状态、完整业务结果、关联记录
  用户操作：手改／恢复／发送等事实、记录 ID、版本与结果
  应用状态：取消／中断／错误等事实
```

具体字段在实现第一个纵向闭环时定稿。完整正文不能只留在临时内存，也不能只保存一个失效后无法还原的 ID。记录引用便于打开当前对象，快照用于还原当时上下文，二者用途不同。

### 4.3 第一版全量上下文契约

每次主助手请求包含：系统说明、当前时间与时区、当前画像／规则，以及本会话完整、有序的模型可见交互。

| 内容 | 处理方式 |
| --- | --- |
| 全部用户消息、助手已输出的内容 | 按顺序保留，不仅取最后六轮 |
| 用户明确添加的资料 | 在加入位置提供正文与元数据快照；邮件头不足时按读取能力取得正文 |
| 主助手的工具调用与工具返回 | 保留参数、调用 ID、成功／失败、结构化结果与引用 |
| 用户手改、恢复、发送等操作 | 作为应用提供的操作事实加入，不能伪装成用户自然语言指令 |
| 被其他会话修改的已引用对象 | 下次请求前比较版本／内容摘要，追加当前状态与内容变化事实，不重写旧快照 |
| 整个邮箱、资料库、其他会话 | 不自动加入，由搜索、读取工具取得本任务所需内容 |
| 网页执行器内部 DOM、点击、网络诊断 | 保存在网页任务；主会话接收结构化最终结果、证据标识与覆盖信息，需要时读取详情 |

全量是主会话业务层的完整上下文，不是每次附带所有浏览器内部日志。首版不做自动摘要或静默丢弃旧轮次；接近模型上下文上限时明确停止并保留记录，提示新建会话并选择所需资料。输入长度限制和输出预算分开配置，不能沿用普通聊天 40000 字限制却声称支持无条件全量历史。

工具结果必须与原调用正确配对。取消、中断导致没有正常返回的调用，要以明确的失败／中断结果闭合后才能继续构建合法请求；不把孤立的工具消息发送给 API。

来源正文、网页和旧模型输出继续作为不可信资料，不提升为系统指令。当前画像更新不追溯修改旧分析；普通聊天不把所有发言自动视为长期事实。

## 5. 主助手与业务工具

### 5.1 不按会话类型裁剪能力

主助手始终获得同一套业务工具定义，按当前目标选择工具和资料。未配置邮箱等情况属于运行能力状态，向模型和用户说明不可用原因，不假装调用成功。

建议工具按实际业务动作划分，名称可在实现时调整：

| 能力 | 建议工具范围 |
| --- | --- |
| 查找与读取 | 搜索／读取邮件、通知、网页结果和草稿；搜索返回元数据，读取返回内容 |
| 通知 | 按用户要求保存通知、保存经过校验的结构化分析 |
| 邮件 | 同步既定范围、读取正文、初筛与保存分析；历史导入保持原有显式范围 |
| 网页 | 执行公开网页查询、读取已保存证据，补查时创建关联的新任务 |
| 草稿 | 创建、读取、按版本更新、复制；字段和地址校验复用现有实现 |
| 记忆 | 读取画像／规则、保存有来源的更新、纠正；保留归属与公开／私人分层 |
| 本轮结束 | 返回最终回答及需要展示的记录引用 |

第一版不向模型提供直接 SMTP 发送工具；由用户点击当前草稿发送。也不自动授予登录、上传或表单提交能力。“全部能力”指当前已授权业务范围，而不是放开外部写操作。

### 5.2 工具执行循环

```text
保存用户消息、资料快照和轮次状态
  → 构建主会话上下文，调用模型
  → 校验工具调用，记录操作开始
  → 执行业务动作，保存业务记录与操作结果
  → 将结果加入主会话，再调用模型
  → 可以接着调用其他类型工具
  → 结束本轮，保存最终回答与关联记录
```

首版工具串行执行，避免先引入并行规划。同一会话一次运行一轮；长任务后台执行，用户切换页面／会话不取消任务，刷新后继续显示状态。不同会话的引用和上下文分别保存，不共享临时聊天变量。现有浏览器同时只运行一个任务的限制先保留，冲突时返回真实忙碌状态，不引入分布式队列。

业务工具返回必须包含稳定记录标识、状态、结果和必要证据，不能只说“完成了”。中间失败作为工具结果交回模型，由它决定继续、换路径或说明缺失；不把任何失败都变成整轮历史丢失。

建议沿用现有 `tool_choice=required` 的路径，新增主会话专用结束工具 `finish_turn(reply, record_refs)`，让普通问答也能正常结束。结束工具不产生业务产物，程序校验引用是否真实存在。现有浏览器工具协议先保持不变，不为了主会话改坏网页执行器。

### 5.3 浏览器与草稿实现复用

网页查询在结构上类似一个浏览子代理：主助手提出明确的子任务，浏览执行器用独立上下文反复调用模型和浏览器工具，再返回结果。这里的“子代理”描述运行职责，不代表需要引入新的多 Agent 框架、另一个模型供应商或独立服务，也不新增面向用户的聊天会话。

当前 `Tasks` 已实现独立的浏览模型循环和后台线程，但由网页任务页面启动，尚未接入统一主助手。此次新增的是父子执行关联与结果交接，而不是从零重写浏览能力：

```text
主助手：理解当前会话，调用网页查询工具
  → 浏览执行器：接收公开目标与范围，建立独立浏览上下文
  → 浏览模型 ↔ 浏览器工具：多步检索、保存证据与进度
  → 返回：任务 ID、状态、结构化结果、证据、覆盖范围与错误
主助手：接收工具结果，继续分析、调用其他业务工具或结束本轮
```

主助手调用业务级网页工具；现有 `Tasks` 执行器继续负责细粒度浏览动作。只有子任务真正到达终态，主助手才把其结果作为本次工具返回并继续后续工作；不能把“已创建 task_id”误当成“已取得官网要求”。网页进度可在等待期间持续展示。

浏览器内部模型获得公开目标、允许公开使用的画像和必要来源线索，不自动接收整个私人会话。查询目标生成仍需遵守私人信息约束，隔离上下文不能被表述为对模型输出绝对不会泄露信息的保证。浏览范围和请求限制继续由现有边界层执行。

草稿由主助手根据当前会话已有证据生成结构化字段，调用确定性的创建／更新操作。无需强制再开一个独立草稿模型会话重复组织上下文。原 `Drafts.assist` 可在迁移期间保留供旧入口使用，统一入口最终不依赖它的独立历史。

来源从当前单一 `source.kind` 扩展为多项 `source_refs`，允许一份草稿同时引用邮件、网页和通知；兼容读取旧 `source`。来源关联不替代实际传给模型的内容，也不作为附件发送。

### 5.4 运行状态、预算与中断

- 一轮状态至少表达运行中、完成、部分完成、失败、取消和中断；浏览器子任务保留自身更细的状态。工具子任务失败与主助手最终回答是否正常完成分别记录。
- HTTP 发起请求返回已接受及轮次 ID；前端轮询执行事件和状态，先复用现有轮询方式，不以引入 WebSocket 或流式文字为前提。
- 网络／模型调用期间不持有全应用的长时间操作锁。原子文件写入保持现有锁，草稿使用现有版本校验；在实际接入时拆除相互嵌套的 `service.operation()`，避免统一调度器和业务方法互锁。
- 取消在当前不可中断调用结束后生效，阻止后续动作；明确展示“正在停止”。已保存资料和已完成修改保留，不伪装成回滚。
- 主助手、网页内部模型等所有真实调用共用日额度，并计入本轮总用量；子任务不能另获一份不计入整体的预算。为最终回答保留收尾预算，额度耗尽时仍展示已完成产物和程序提供的状态事实。
- 进程重启后将未完成轮次标记中断，不自动重放写操作或付费调用。持久化保留可见进度，用户可以明确发起后续轮次。
- 业务写入与会话结果写入不是跨文件事务。操作先记录目标与关联标识，再执行和记录结果；重启后对尚无确认结果的操作按已有记录核实或标注待核实，不自动创建重复草稿，不承诺恰好一次。复用已有持久化机制，不新增通用事务／事件总线框架。

## 9. 首版实际落地与验收入口

### 9.1 实现位置与具体选择

- `assistant/conversations.py` 实现按会话保存的事件序列、后台轮次、工具循环、取消、完整上下文、旧聊天导入和中断处理；业务操作元数据直接放入会话，不另建一套运行数据库。
- `assistant/records.py` 实现搜索、统一表示和快照。引用采用 `{kind, id}`，草稿快照额外记录版本；`fingerprint` 用于发现跨会话内容更新。业务内容仍保存在原目录。
- 主助手通过 `finish_turn` 结束本轮；业务工具包括资料搜索／读取、通知保存／分析、邮件头初筛／分析／画像建议、既定范围邮件同步、网页查询／证据读取、草稿创建／更新／复制和明确用户记忆更新。直接发送工具不提供给模型。
- 浏览器沿用 `Tasks` 的独立模型循环，通过 `origin` 关联主会话和轮次，限制子任务可用调用数，预留主助手返回回答的预算。完成或失败后都把实际结果交回主会话，不再为这些任务创建独立临时追问。
- 统一工具的单次浏览默认最多12次内部模型调用，主助手可用 `max_calls` 调整，仍受浏览器、本轮和日额度上限约束；避免一次浏览默认耗尽所有额度而无法继续起草。旧独立网页接口的配置上限保持原样。
- 草稿多来源使用兼容的 `source={kind: records, refs: [...]}`，同时存储 `source_refs`；旧来源和版本不迁移重写。通过聊天创建／复制的草稿另存 `origin`，记忆历史记录用户原话及对应会话／轮次。
- 详情编辑使用800毫秒自动保存；切换会话／记录、关闭面板、发送前等待保存。尚未保存的输入及其基准版本保存在本标签页 `sessionStorage`；冲突时保留输入并允许用户明确重新载入，不拿旧输入静默覆盖新版本。
- 未发送聊天输入及所选资料按会话保存在 `sessionStorage`，当前会话 ID 保存在 `localStorage`。完整已发送历史在服务端 JSON 中，不依赖浏览器缓存恢复。
- 手改、恢复、复制、发送和设置中的记忆编辑通过 `X-Conversation-ID` 关联当前会话；服务端先检查会话，再执行并记录实际结果。无变化的草稿自动保存不反复追加事件。
- 画像／规则可在设置中展开修改历史，核对变更前后内容并恢复到变更前；恢复本身保存新历史，不删除旧变更。主助手也可按用户要求读取记忆历史，再用有用户原话来源的更新工具纠正。
- 执行记录默认折叠；最终回答下面按对象去重展示关联结果。运行中或回答失败时，已产生记录仍然可打开。历史版本提示与当前详情分开，旧快照不会被覆盖。
- 旧 `chat.json` 自动兼容导入一次，原文件保留，`conversation-migration.json` 保存导入标记。删除导入后的会话不会在下次启动重复导入。旧邮件、通知、网页、草稿和发送记录可以直接选择。
- 各功能页面的独立聊天框已移除。旧 `/api/chat`、`/api/followups`、草稿独立 assist 等 HTTP 接口暂留，供既有客户端与回归兼容；新主界面不调用这些聊天接口，不需要为此一次删除整个旧服务实现。

5. 刷新、切换会话及重启，核对已保存历史和产物。运行中停止任务后，核对已完成结果保留且没有继续执行。

用户已初步进行真实 API 和跨类型任务验收，反馈基本良好；实际模型的资料使用质量和后续修正效果仍需继续验证，不由离线通过推断。首版保留纯文本回答、普通关键词搜索、轮询进度、单浏览任务和完整上下文；没有新增流式文字、自动摘要或附件解析。

### 9.4 初步验收后的草稿完善（2026-10-30）

- 通过提示词约束个人事实与附件措辞：不得编造个人信息，缺少必要信息先向用户确认；纯文本邮件不声称已经附带文件。需要用户准备的附件放在草稿之外的最终回答说明中，不增加正文关键词过滤器。
- `source_refs` 是草稿实际参考资料的导航入口，不是附件列表，也不保证事实已核实。主助手创建时应列出实际使用的邮件、通知与网页任务；修改工具新增可选 `source_refs`，与已有来源去重合并。不传该字段时保留来源，不自动把所有读取过的资料都列为依据。
- 来源增补也产生新版本；新版本保存来源快照，恢复时一起恢复。旧版本没有来源快照时保留当前来源，旧文件不批量迁移、不回填猜测的来源。历史会话快照仍保留原样。
- 草稿详情在编辑区上方显示“草稿来源”、资料类型与标题，点击直接查看原记录；标题读取只访问本地已保存元数据，不触发邮件正文下载。历史列表显示“助手修改／手工修改／恢复历史”等类型。
- 本人邮箱背景已接入：从 `QQ_IMAP_USER` 配置生成 `background.mail_account.address`，放在每次主助手模型请求中，包括工具循环中的继续请求；只含地址，不包含授权码、不写入长期画像，也不自动传给浏览子任务。未配置时省略该字段，提示词要求询问用户，不猜测本人地址。
- 邮件分析事件的工具定义明确要求两种引用方式至少一种：非空 `evidence` 原文，或 `line_start` 与 `line_end`。统一邮件资料增加 `numbered_lines`，沿用旧入口的原文提取机制；缺少引用时返回明确补充要求，原文匹配、时间证据及带时区检查继续保留。旧记录不迁移，已取消任务不自动重跑。
- 提示词采用通用表述，移除求职等场景举例和重复清单。主助手、兼容草稿入口、浏览及私人分析阶段统一要求不得编造个人信息，缺少必要信息先确认；网页子任务把问题放在 questions 中交回主助手。工具字段约定放入工具说明，系统提示词只保留职责、基本原则与必要流程。
- 主助手模型事件新增 `system_template_sha256`，标识发起请求所用静态 system 模板，不包含动态私人背景。离线测试检查实际 HTTP 请求 JSON 在工具执行前后均携带完整模板；旧事件无此标识，不反推旧请求。修改代码后须重启应用，运行中服务不会自动载入新提示词。

### 9.5 模型如何获知能力与工具

主会话每次请求分别提供 system 通用规则、动态背景与完整会话消息，以及 API 的 tools 字段。工具定义包含名称、用途、参数类型、必填项及限制，不需要在 system 中重复整份清单。动态背景中的 capabilities 是接入状态，不是工具清单。当前正常请求提供16个业务工具；只剩一次调用预算时，仅提供 finish_turn 并提示收尾。

| 调用入口 | 能力说明与可用工具 |
| --- | --- |
| 主会话 | `conversations.SYSTEM` + 时间、画像、邮箱及接入状态 + 业务 tools。可检索／读取资料、保存通知和分析、邮件初筛／同步／画像建议、委派浏览、管理草稿及明确要求的记忆、回复或提问；无发送工具。 |
| 网页任务 | `tasks.TASK_SYSTEM` + 公开目标／范围／来源／预算 + 浏览工具；私人分析阶段使用 `ANALYSIS_SYSTEM`，仅提供来源读取、返回浏览及结束工具。 |
| 兼容邮件分析 | `mail.MAIL_SYSTEM` + 当前邮件及编号行 + 画像建议／保存分析工具。 |
| 兼容追问 | 使用 `followup` 自身提示词与阶段工具。分析时可读取来源、委派公开浏览和结束回复；浏览时只提供浏览操作及 return_to_followup，不继承普通网页任务的结束或切换工具说明。 |
| 兼容文本调用 | `llm.SYSTEM` 明确本次没有可执行工具，再拼接通知分析、邮件头初筛、普通问答或草稿的具体任务与JSON格式。 |

工具参数说明负责必要细节：独立浏览目标须自洽、记录引用采用已知ID、记忆按公开检索／私人分析／纠正规则分层、草稿来源按实际使用资料记录。系统规则保持通用，个人信息未知时先询问。离线验证检查实际 HTTP JSON 中的工具定义、首次及后续请求、预算收尾，以及兼容追问的阶段工具；不以此保证真实模型的工具选择与回答质量。

### 9.6 资料展示完善

- 资料选择器的预览与会话旁详情共用内容渲染。邮件／通知展示分析摘要、事项、时间、建议行动、待确认和原文；草稿预览为只读字段与正文；网页任务展示状态、查询要求、结果、引用与结束说明，不以JSON代替业务内容。
- 保存的网页逐页折叠，显示标题、URL、保存时间、正文行数及读取状态，展开后按行展示原文。结果中的“定位原文”打开对应页面并高亮引用行；原文仍完整保留，不用模型摘要替换，也不声称清除了导航或验证了事实。正文行在展开时才创建，避免默认铺满全部页面文本。
- 浏览动作呈现步骤列表，包含动作名称、参数、成功／失败状态、保存来源及错误；诊断按网络／页面交互等类型整理。会话执行过程展示资料链接、摘要和错误，原始返回与诊断JSON保留在默认关闭的“原始调试数据”中。
- 邮件列表显示分析状态，预览和详情在分析为空时明确说明。使用邮件作为链接来源不等于保存过分析；已有分析会展示，缺失分析不会在查看时自动生成或猜测回填。
- 预览的标题／关闭按钮及打开详情入口在长内容滚动时保持可用。合成浏览器流程覆盖无分析／有分析邮件、网页结果预览、引用定位、失败动作与调试折叠、会话执行展示、草稿编辑和手机布局，不读取真实账号。
