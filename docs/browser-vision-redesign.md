# 网页代理：视觉与直接浏览器操作改造方案

后续决策更新：用户已确认采用持久Python会话直接执行原生Playwright，替代本草案最初建议的通用动作工具。现阶段实现、Docker/local边界与验证情况以 [持久Python网页子代理](browser-runtime.md) 为准；以下保留方案讨论与手工实测依据。

2026-11-03。状态：方案草案，尚未实现；替代继续扩充旧控件规则的方向。当前分支 `fix/browser-interaction`，本方案不代表已验收或允许合入 main。

## 目标与范围

让网页代理通过当前截图、页面语义和浏览器操作，连续完成搜索、展开菜单、选择配置、检查状态、读取对应价格。模型负责选择路径、判断变化和恢复；执行层准确执行、报告事实，不替模型判断任务是否完成。

保留独立网页子代理、统一聊天入口、任务记录与资料引用。主助手委派网页目标，网页代理直接控制浏览器；无需主助手逐步批准点击。第一阶段仍限公开查询，不扩大到登录、私人表单、下单和发送。验证码不保证可解决。

## 依据：当前实现和已复现问题

- `assistant/tasks.py` 已通过标准 tool calling 执行模型选择的动作，并非固定流程或额外模型规划器。需要精简的是工具与浏览器之间的封装，不是重新做一套自然语言命令解析器。
- 已存在 `take_screenshot`、图片消息传递及最近两张图片的上下文保留；`browser_vision` 默认关闭，截图也须模型单独请求。当前截图遮罩全部输入框，可能遮住搜索状态。
- `JobBrowser` 多数动作内部直接调用较重的 `observe()`。因此动作执行成功后，正文采样或整页扫描失败，仍可能被当作动作失败。
- 最新任务第7、8步是正文读取的2000ms超时；第11、12步才是导航超时。手工复现已读到约两万字，后一次采样超时却丢弃本次观察；随后再次观察成功。尚不能确定单次读取阻塞的底层原因。
- 原生radio的关联标签处理仅用于 `check_field`，`click_element` 仍可能点击被标签遮挡的input。旧元素编号、候选提取和限定文字匹配增加了模型恢复成本。

这些问题支持重构交互链路，但不能据此证明视觉模型可以稳定完成所有网站。

## 设计选择：直接操作的含义

推荐第一版采用标准工具调用，工具参数直接映射 Playwright 能力，加入截图坐标操作；不解析助手普通回答中的指令。保留一个薄的参数校验与执行入口，去除按业务场景分类控件、要求整页稳定才能返回等中间决策。

模型自由生成 Playwright/Python 程序是另一种方案：表达力更强，但运行在应用进程中的 `exec` 会获得该进程的文件、凭据和网络权限。删掉几个内置函数不是隔离；放进普通子进程也不构成安全隔离。网页内 `page.evaluate` 则是浏览器页面上下文中的JavaScript，不能与服务器上的Python/Shell等同，也仍可能触发网页请求或写操作。

第一版不新增通用服务器代码执行器，也不提供通过任意网页JavaScript绕过原有操作授权的入口。如果通用工具在验收中仍有明确表达缺口，再单独设计持久浏览器脚本运行时，明确隔离与权限成本，不靠不断增加专用工具补洞。该取舍是实施建议，尚待用户确认方向。

## 交互架构

```text
主助手：网页目标、范围、所需结果
    ↓
网页代理：多模态模型决定下一步
    ↕ 标准 tool calls / 文字反馈 + 图片
薄浏览器接口：定位、鼠标、键盘、标签、观察、取证
    ↓
现有 Chromium + 网络连接/授权边界
```

工具提供通用能力：导航；观察；点击、悬停、填写、按键、勾选、原生select选择；滚动；标签页管理；有条件等待；读取及保存证据；结束任务。动作可以使用角色与名称、label、文字、CSS定位，或截图坐标。允许作用域定位和明确的匹配序号，避免相同名称时任意选中第一个。

不再要求目标必须出现在自定义的200个元素候选中。旧元素编号可在迁移期间保留，最终不作为唯一定位方式。不按文案或某个网站创建新的业务动作；公开搜索和配置选择共享通用能力。

### 观察与执行分离

- `observe` 默认提供当前视口截图、URL、标签、视口尺寸、滚动位置、页面语义与可见状态。全文、链接及深层DOM按需补读，不每次重传整页。
- `act` 先记录操作本身的结果，再获取一次轻量观察；不用反复读取全页正文等待稳定。动作成功而观察失败，分别报告，不覆盖动作事实。
- 正文采集保留已取得的快照；后续采样失败，记录时间、截断和读取警告。正文读取失败时仍可尝试返回截图；截图失败也不能伪装成模型已看到图片。
- 分开记录 `action_status`、`observation_status`、`verification`。前两项由执行层报告；verification可以是checked/value等直接状态，或由模型比较前后观察得出的结论。点击完成不等于价格已经更新。
- 等待由模型选择：指定可见文本、控件状态，或等待一段时间后重看。导航、动作、观察有独立且清楚的超时，不把 `networkidle` 或全文稳定作为所有动作的前提。保留取消与总预算。
- 模型可连续操作已知且互不依赖的目标；需要根据新界面决定的步骤先取得观察。不新增“每回合只准一次动作”的硬规则，也暂不增加复杂批量执行语言。

### 视觉和坐标

第一版使用固定CSS视口与明确的截图尺寸。每张观察带 `observation_id`、`tab_id`、URL、截图时间、CSS视口大小与图片像素大小。坐标工具引用对应观察，以截图像素坐标输入，由执行层换算CSS坐标；滚动/导航/切标签后使用新观察。拒绝属于已知旧页面状态的坐标，并返回新观察，不进行猜测点击。网页自行变化无法完全检测，仍需模型核对结果。

角色、名称和label定位便于精确操作；坐标点击用于视觉上可见的自定义控件。两种方式均通过正常浏览器鼠标/键盘动作，不靠强制点击穿透遮挡。保留原生locator的自动等待与明确错误，不自造一套点击算法。

截图成为浏览阶段常规输入：初始打开、改变界面的动作后、恢复错误时提供。最新两张作为初始保留策略，旧图从模型请求移除，但保留本地记录。DOM、截图不是原子快照，记录采集次序，遇到导航中断明确说明。

匿名公开浏览不统一遮住全部搜索框；展示公开搜索文本与选择状态。继续不加载用户日常浏览器账号和密码；如未来允许私人输入，届时按实际隐私需求重新设计遮罩，不在本轮引入猜测性分类器。

### 模型与上下文

当前复用 `APIModel` 的多模态content和tool calling传输。可选网页模型配置覆盖model/base_url/key，未填写则继承主模型；不强制拆成独立服务或框架。网页端点必须实际支持图片与工具调用，不能仅凭OpenAI兼容URL判断。

真实接入先验证“图片辨认 + 工具调用 + 下一轮读取工具结果和图片”的最小往返。失败时明确说明不支持的能力，不静默退成纯文本模式。当前具体端点的视觉能力尚未验证，不在文档中声称可用。

截图编码长度不等于图片tokens。保留服务商返回的usage；请求前计数仅在端点确实支持该多模态格式时使用。不要将主助手当前上下文百分比与独立网页任务用量混合。

浏览上下文保持任务目标、简短动作记录、最新观察及所需证据；保留私人分析与公开浏览的隔离。本轮不重写主会话上下文管理。

### 证据与用户看到的结果

沿用现有任务、正文编号行和资料引用，不要求一开始迁移私人历史文件。新记录增加可选观察引用与动作/观察各自状态，旧记录继续显示。

动态价格取证保存当时选中的配置、URL、时间、可见价格文本及对应截图，绑定同一观察。截图作为视觉核对依据；不能用隐藏DOM标签证明价格，也不能把某配置的价格与另一配置拼接。若只能视觉识别、没有可引用文字，明确标记视觉来源及未核实项；扩展结果结构支持这种证据，不能伪造正文行号。

界面继续显示任务进度与最终资料，步骤可查看“操作前/后截图、目标、是否执行、观察是否成功、核对到的变化”。常规展示不露出整段原始JSON；详细网络诊断留在调试折叠项。此次不新增实时远程桌面。

| 5. 真实验收与清理 | 用户接API；固定任务对照新旧表现，删除被替代的控件规则与工具接口，同步README。 | 连续操作闭环通过后再请求合入main；不推送、不部署。 |

## 验证和完成标准

离线测试使用合成页面：尺寸、芯片、内存选择影响价格；关联label、自定义控件、延迟更新、遮挡、滚动、新标签和观察超时。检查最终配置与价格对应，不只检查工具返回成功。

真实API由用户验收，至少包含：苹果购买页连续配置选择并读取价格；Bing搜索后打开来源核对；另一个不同布局的公开配置/筛选页。苹果页面若网络失败，单独记录导航问题，不能拿合成页通过来宣称已解决。

记录任务完成与否、选择是否真的生效、价格是否匹配、无效动作与恢复次数、模型调用与usage、总耗时。初始不承诺成功率或任意网站可用；当前日志不是可比较的完整基线。人工使用同一运行环境的浏览器作参照，区分网络、站点验证、执行层和模型判断问题。

通过标准：模型能看到当前界面，连续完成所需选择并核对结果；失败阶段与实际浏览器状态相符；结果证据可追溯；已有资料引用及任务取消不退化。视觉模型的效果是待验证假设，不能把增加截图本身当作完成。

## 直接浏览器实测后的修订

用户要求绕过项目执行层亲自操作。已使用独立Playwright会话直接控制Chromium，没有导入应用模块、调用Kimi API、修改网页状态或执行购买。通过截图观察决定鼠标点击与滚动，同时使用原生locator读取状态和精确定位。用户确认体验足够后停止，浏览器已关闭；没有完成全部型号和配置调查，不宣称完整任务验收。

已完成的交互链路：从Mac目录查看产品介绍，直接进入观察到的购买URL，选择14英寸、颜色、标准玻璃、M5 Pro及具体处理器，再展开内存和存储，切换内存、2TB和4TB存储并读取变化后的价格。这证明该页面在本次环境下具备正常交互路径，不证明Kimi在同等输入下必然成功。

得到的实施依据：

1. 截图提供清楚的配置卡片和编辑入口，正常鼠标点击可以选中被关联label覆盖的radio。无需先识别input类型、调用专用修复分支才允许操作。
2. 原生locator同样有用：滚动与布局变化后，一次坐标点击没有改变存储选择；检查状态后，改为按可见label定位成功。不能将视觉理解等同于所有动作都必须走坐标。
3. 内存选中状态先改变，500ms时顶部仍为旧价格；后续观察才出现新金额。因此不能以工具调用返回或checked=true证明价格同步完成，必须比较目标输出。
4. 页面滚动/展开动画会使截图中的位置继续变化。获取观察时允许短暂界面采样，但不以整页正文稳定或全网请求完成为前提；坐标操作后仍检查实际变化。
5. 直接Playwright仍遇到重复链接的strict mode错误，以及产品介绍页一次后续DOM读取长时间无响应。通过阅读错误、改定位与打开已知购买URL恢复。原生执行不是无错误执行，重点是信息足够并允许灵活恢复。
6. 此次手工会话通过Python执行原生Playwright代码，具备临时查询DOM和组合动作的自由，不能将其结果直接算作拟议工具接口的验证。实施验收应检查新工具是否保留了这些实际用到的表达能力，而非仅复刻工具数量。

调整实施重心：先实现能表达此次操作的薄浏览器接口和常规视觉循环，减少旧候选列表及场景规则的依赖；沿用已有Chromium生命周期和任务记录。网络权限与连接层单独核对证据，不因本次直接浏览成功就整体删除，也不把新旧表现差异归因于尚未隔离的因素。代码运行时仍作为独立取舍，不能以“像本次手工会话”声称第一版已提供任意脚本能力。

原始截图、文字和临时会话脚本仅存于忽略的 `data/debug/`，不提交私人调试材料。
